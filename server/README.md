# Локальная авторизация AURA

ASP.NET Core 8 + SQLite + Argon2id (64 МиБ, 3 прохода, 2 потока). Пароли хранятся как соль и хеш; ключи лицензий, login-токены и session-токены — как SHA-256 от случайных значений длиной 256 бит. Ключ активации одноразовый, login-токен живёт 10 минут. Лицензия привязана к аккаунту и устройству; успешные ответы подписаны ECDSA P-256.

Сессия действует до окончания лицензии или отзыва. После выхода её токен отзывается сервером; если связь отсутствовала, локальный файл всё равно удаляется, удалённый отзыв не подтверждён. Повторный вход на том же устройстве создаёт новую сессию для существующей лицензии. Отозванную/истёкшую лицензию сервер не принимает. Подписанный офлайн-грант живёт не более 24 часов и не дольше лицензии. Поэтому отзыв не может немедленно достигнуть отключённого от сети клиента. Проверка в открытом приложении — каждые 15 минут. Устройство — хеш Windows MachineGuid, а не доказательство защиты от администратора ПК.

## Запуск и создание данных

Из корня репозитория:

```powershell
dotnet restore Aura.sln --locked-mode
dotnet build server/Aura.AuthServer -c Release
$env:ASPNETCORE_ENVIRONMENT = 'Development'
$env:Aura__DataDirectory = [IO.Path]::GetFullPath('./server-data')
dotnet run --project server/Aura.AuthServer -c Release --no-build -- --urls http://127.0.0.1:5088
```

HTTP разрешён только для loopback-запроса в Development. Без этого сервер отказывает в HTTP-запросах. `/health` возвращает `status=ok` и версию протокола; это техническая проверка, не публичная страница.

В другом терминале с тем же `Aura__DataDirectory` создайте аккаунт и лицензию. Пароль и ключ для отзыва вводятся интерактивно без отображения. Не используйте реальные секреты как аргументы или значения в истории команд.

```powershell
dotnet run --project server/Aura.AuthServer -c Release --no-build -- admin account
dotnet run --project server/Aura.AuthServer -c Release --no-build -- admin license 30
dotnet run --project server/Aura.AuthServer -c Release --no-build -- admin public-key > server-public-key.txt
./scripts/configure-auth.ps1 -Mode LocalDevelopment -BaseUrl http://127.0.0.1:5088/ -PublicKeyFile server-public-key.txt
```

Лицензионный ключ сохранится в отдельный защищённый файл в каталоге данных; CLI показывает только путь. Передайте его владельцу выбранным защищённым способом. Не добавляйте этот файл в Git. Для отзыва: `admin revoke`. Административного HTTP API и аккаунтов по умолчанию нет. Затем пересоберите Windows EXE. Открытый ключ не секрет; его подмена меняет доверие клиентской сборки, поэтому его проверяет издатель.

`auth.db` и `signing.key` должны храниться вместе в закрытом каталоге. Unix: 0700 для каталога, 0600 для ключа/базы. Windows: доступ владельцу процесса и SYSTEM, наследование отключено. Сделайте защищённые резервные копии SQLite и ключа; копирование живой SQLite-базы без WAL/backup API недопустимо. Утрата ключа делает прежние подписи недействительными; смена ключа требует новой клиентской сборки. Для нескольких реплик нужна общая транзакционная БД и единое хранилище ключа — текущий вариант для одного узла.

## HTTP-контракт

POST JSON:

- `/v1/login`: `email`, `password`, `deviceId` → loginToken либо существующая подписанная session.
- `/v1/activate`: `loginToken`, `licenseKey`, `deviceId` → session.
- `/v1/validate`: `sessionToken`, `deviceId` → обновлённая подписанная session либо отказ.
- `/v1/logout`: `sessionToken`, `deviceId` → отзыв сессии.

Секреты не передаются в URL и не записываются приложением в журнал. Не включайте логирование тел запросов на reverse proxy. Размер запроса ограничен 16 КиБ, лимит на IP — 10 запросов в минуту, одновременно обрабатываются не более 8 запросов. Ошибки аккаунта/ключа возвращаются общим сообщением.

## Размещение позже

Домена и хостинга пока нет; сервер подготовлен локально, публичного сервиса нет. Для размещения нужны HTTPS-сертификат сервера, закрытый постоянный том, резервное копирование и корректное время. Используйте TLS прямо на Kestrel либо TCP-прокси, сохраняющий TLS. Пример настроек Kestrel: `ASPNETCORE_URLS=https://0.0.0.0:8443`, `ASPNETCORE_Kestrel__Certificates__Default__Path=<закрытый путь к PFX>`; пароль задаётся через защищённое окружение. Это отдельный сертификат от Authenticode для EXE.

Dockerfile собирается из корня: `docker build -f server/Aura.AuthServer/Dockerfile -t aura-auth .`. Контейнер работает от стандартного непривилегированного APP_UID образа .NET. Подготовьте том `/data` с доступом этому UID, отдельно подключите закрытый сертификат и укажите HTTPS-настройки. HTTP на внешнем интерфейсе запрещён. Перед публикацией используйте production-окружение, настройте клиент в режиме Server с HTTPS и соответствующим открытым ключом, выполните интеграционные проверки.

Тесты: `dotnet test tests/Aura.AuthTests -c Release`. Проверяются реальный ASP.NET HTTP-конвейер и клиент, одноразовость/гонки активации, неверный пароль/ключ/устройство, подпись, срок, сохранность при рестарте, отзыв и офлайн-ограничение. Docker-запуск и публичное TLS-размещение требуют отдельной проверки.

В этой облачной среде Docker daemon доступен, но загрузка официального образа была отклонена сетевой политикой на `westus.data.mcr.microsoft.com`. Docker-образ здесь не собран и не запущен. Для повторной проверки нужен доступ к CDN `*.data.mcr.microsoft.com`; локальный запуск самого сервера без Docker и HTTP-интеграционные тесты выполнены.
